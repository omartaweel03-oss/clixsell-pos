=====================================================================
الخلاصة بسرعة
=====================================================================

الجزء الأساسي جاهز ومختبَر ويعمل فعلاً من الشاشة حتى قاعدة البيانات:
  - تسجيل الدخول والصلاحيات
  - تعدد المتاجر
  - إدارة المنتجات
  - شاشة البيع POS: البيع، التعليق، المرتجع، إيصال QR

الناقص بالكامل:
  - التقارير والتحليلات
  - Guardian Mode والذكاء الاصطناعي
  - أوامر الشراء وواتساب
  - العمل بدون إنترنت
  - كاميرا الباركود
  - تطبيق Android

ثلاث ملاحظات مهمة:
1) البنية تختلف عن التقرير. التقرير (ص 8-9، و 56) يتكلم عن Firebase مع SQLite
   محلي ومزامنة. المشروع الحالي Spring Boot مع SQLite على السيرفر، حسب طلب
   الدكتور: "Product Screen <-> API <-> business logic <-> DB".
   لازم تكون جاهز تشرح هذا الفرق للدكتور.
2) الـ ERD (ص 46) فيه حقل cost_price للمنتج، وهو غير موجود عندنا.
   بدونه لا يمكن حساب الربح المطلوب في شاشة التقارير (Fig 3.8).
3) لا يوجد مجلد android/ ولا ios/ في المشروع. الموجود فقط web/ و macos/،
   بينما التقرير (ص 27، Portability) يقول إن التطبيق يجب أن يعمل على Android.

5. تسجيل الدخول (Authentication)
=====================================================================

1) الجميع يستخدم نفس شاشة Login. يتحقق AuthService من اسم المستخدم وكلمة
   السر المخزّنة كـ BCrypt hash.
2) عند النجاح يُنشأ token عشوائي 256-bit. يُخزَّن فقط الـ SHA-256 hash،
   والجلسة صالحة 12 ساعة.
3) التطبيق يرسل الـ token مع كل طلب:  Authorization: Bearer <token>
   يقرأه TokenAuthenticationFilter ويحوّله إلى CurrentUser
   (userId، role، storeId).
4) إذا رجع السيرفر 401، يرجع التطبيق تلقائياً لشاشة Login (auth_session.dart).

حماية الحسابات:
  - 5 محاولات خاطئة تقفل الحساب 5 دقائق.
  - تعطيل المستخدم أو متجره يُخرجه فوراً.
  - تغيير كلمة السر يُنهي كل جلساته.

أول System Admin: يُنشئه SystemAdminInitializer عند أول تشغيل:
  sysadmin / Admin12345

صلاحيات كل دور (مفروضة في SecurityConfig.java وليس في الواجهة فقط):
  - System Admin : المتاجر ومدراؤها فقط، بدون منتجات أو بيع
  - Store Admin  : المنتجات، الكاشيرية، البيع
  - Cashier      : البيع، وقراءة المنتجات فقط

مقارنة مع التقرير:
  SR1 (username/email) -> [PARTIAL] باسم المستخدم فقط
  SR2 (تحديد الدور)     -> [FULL] مع توسيع: Manager = Store Admin، وأضفنا System Admin

6. تعدد المتاجر (Multi-Store)
=====================================================================

- كل منتج ومورّد ومستخدم وفاتورة ومرتجع مرتبط بـ store_id.
- المتجر يُؤخذ دائماً من المستخدم المسجّل دخوله (CurrentUser.storeId)، ولا
  يُؤخذ من الطلب أبداً. لو أُرسل storeId مختلف يتم تجاهله
  (اختبار storeIdInTheRequestBodyIsIgnored).
- الوصول لسجل من متجر آخر يرد 404، فلا يعرف المستخدم حتى أنه موجود.
- الباركود واسم المورّد فريدان داخل المتجر فقط. وكل متجر له ترقيم فواتير
  خاص يبدأ من INV-000001.
- الكاشير الجديد ينضم دائماً لمتجر المدير الذي أنشأه.
